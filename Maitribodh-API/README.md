# Maitribodh Access Management System API

Node.js 22+ and Express 5 API for the Maitribodh Access Management System.

## Local setup

1. Install dependencies with `npm ci` from the committed lockfile.
2. Set `DATABASE_URL` for a PostgreSQL 16 instance.
3. Set `JWT_SECRET` and `QR_HMAC_SECRET` to separate random secrets of at least 32 bytes; production values belong in AWS Secrets Manager.
4. Set `LOGIN_RATE_LIMIT_WINDOW_MS` and `LOGIN_RATE_LIMIT_MAX` from the approved environment policy. The server intentionally has no implicit login-rate threshold.
5. Set `UI_ORIGIN` to the exact allowed frontend origin and enable `DATABASE_SSL=true` in production.
6. Run `npm run migrate` to initialize migration tracking and apply reviewed SQL files.
7. Run `npm test`, `npm run lint`, and `npm start`.

The API includes authentication, user/master-data operations, person search, approvals, QR lookup, gate/visit operations, blacklist management, dashboard summaries, and reports. Never commit secrets or local environment files.

## Registration and activity workflows

Migration `0004_registration_workflows.sql` adds persisted category field schemas, registration drafts, access expiry, and append-only audit enforcement. Apply any later migrations with `npm run migrate` before restarting the API. Existing data is retained.

`GET /api/v1/persons/registration/options` supplies active master data and category schemas. `POST /api/v1/persons` accepts multipart `metadata` (JSON), one required `photo`, and optional `documents`. Images are decoded and resized to at most 600 pixels; each input file is limited to 5 MB. Set `UPLOAD_DIRECTORY` to a private, backed-up directory outside the web root. The default is `private-uploads` relative to the API working directory. Files are served only through authenticated person-file routes, not a public static directory. This is local-disk storage, not an S3 integration.

Set a stable `DATA_ENCRYPTION_SECRET` for encrypted passport and ID-proof storage. If omitted, the configured QR HMAC secret is used as the input to a separate encryption-key derivation. Do not rotate that source secret without a data-key migration. Drafts intentionally omit passport and ID-proof numbers and file bytes; enter those again when resuming.

Registration writes the profile, area assignments, approval history, audit and notification rows in one transaction. Failed writes remove newly uploaded files. Guards can register visitors only and cannot assign areas at registration. Mobile changes advance QR versions to invalidate earlier signed codes. Duplicate person mobiles remain allowed, matching the attached mockup and existing fixtures.

New read routes include person detail/activity, per-user notifications, and administrator audit browsing. Notification read updates always use the authenticated user ID. Audit records have no update/delete routes and the new database trigger rejects modifications.

See `../docs/MAMS_IMPLEMENTATION_STATUS.md` for remaining feature gaps and verification limits.

## Local development API

From the API directory, run `./db/start_dev_api.ps1`. It prompts for the local PostgreSQL password without echoing it, generates temporary development JWT and QR secrets, and starts `src/server.js`. Those runtime secrets are cleared from the PowerShell environment when the process exits.

## Local development fixtures

On a disposable loopback development database only, run `./db/seed_dev.ps1` from the API directory. It prompts for the local PostgreSQL password and a strong Super Admin bootstrap password without echoing or saving either value. The seed refuses production mode, non-loopback databases, weak passwords, non-empty core tables, or an existing seed marker. It creates synthetic fixtures across MAMS tables and stores only a bcrypt hash for the Super Admin password, which expires after 24 hours and requires password change at first login. Photo/document fixture keys are placeholders; no object-storage files are created. Do not run this seed on a shared or production database.

After the main dev seed, optionally run `./db/seed_demo_users.ps1` to add the mockup role accounts: `s.iyer` (Admin), `r.sharma` (Security Guard), `a.verma` (Registration Officer), `n.das` (Approver), and `k.rao` (Viewer). It prompts for a shared strong demo password; each account stores only a bcrypt hash and is forced to change that one-time password at first login. User IDs are generated by PostgreSQL and printed after seeding. The actual `gotam.pandey` Super Admin remains a separate account. This helper is loopback-only and refuses partial/duplicate demo users.
